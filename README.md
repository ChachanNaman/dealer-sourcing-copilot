# Dealer Sourcing Co-pilot

A sourcing co-pilot for used-car dealers bidding on auction inventory. A dealer
describes what they want in plain English; the system finds matching cars and
computes a **recommended maximum bid** for each — predicted retail minus refurb,
holding, fees and the dealer's own margin target — and shows the reasoning
behind every number.

> **Synthetic data — no CARS24 data was used or accessed.** Every car, price and
> sale in this project is generated by a seeded simulator (`api/app/generate_data.py`).
> This is not affiliated with, endorsed by, or built for CARS24; it borrows the
> rebranded *design language* only. The metrics below measure the model on this
> synthetic data — they are **not** a claim about real-world accuracy.

## The design principle

> **The LLM parses language. A model computes the number. Rules make the
> decision. The dealer confirms it.**

The language model only ever emits search *filters* — never a price, valuation
or bid. That boundary is enforced twice: a pydantic schema with `extra="forbid"`,
and an explicit price-leakage assertion on the raw model output. Pricing is done
by a separate gradient-boosting model plus a deterministic cost formula. A bad
LLM parse can only produce wrong *filters* (which the dealer sees as chips and
can remove) — never a wrong *bid*.

## Measured numbers

Copied exactly from [`api/models/metrics.json`](api/models/metrics.json),
held-out test set of n = 2000:

| Model | Metric |
|---|---|
| Retail price | **MAE ₹19,121 · 3.88% MAPE** |
| Days to sell | **MAE 4.6 days** |

**Intent parsing eval:** 30 / 30 queries routed through the live LLM, **100%
field accuracy (360/360 fields)**, **0 / 30 price leakage**.
These 30 queries are **regression cases I hand-authored** (`api/evals/queries.json`)
to guard the parser and the price-leakage boundary — they are *not* a held-out
benchmark, and 100% on them is a correctness check, not a generalisation claim.

**Pricing behaviour across the 4,000 synthetic listings:** 37.0% have positive
headroom at the default economics, median expected margin ₹39,450, and 6.2% fall
below the comparable-sales threshold and are refused a price (shown as
"not enough data" cards rather than guessed).

## Architecture

```
Dealer types a sentence
        │
        ▼
┌─────────────────────┐
│ intent.py           │  LLM → strict JSON filters
│  (the ONLY LLM call)│  retry once, then keyword fallback
└──────────┬──────────┘
           │ filters (no price ever)
           ▼
┌─────────────────────┐
│ search.py           │  deterministic filter over auction_inventory
└──────────┬──────────┘
           │ candidate listings
           ▼
┌─────────────────────┐
│ pricing.py          │  GB model → predicted retail + days-to-sell
│                     │  cost formula → max_bid, margin, headroom
│                     │  comparables count → confidence
└──────────┬──────────┘
           │ priced candidates
           ▼
┌─────────────────────┐
│ ranking.py          │  drop headroom<=0 and confidence=="low"
│                     │  blended score 0.5 margin / 0.3 velocity / 0.2 conf
└──────────┬──────────┘
           ▼
     JSON response + trace_id
           │
           ▼
      React UI (cards, why-panel, economics)
```

Every recommendation carries a `trace_id`; `GET /trace/{id}` replays the full
chain (raw query → raw LLM output → parsed filters → candidates → scoring → final
output). The economics (margin, holding, fees, refurb) travel in the request
body, so changing them is a stateless re-request and the bids re-rank live.

## Implementation notes

- **LLM: Groq, model `openai/gpt-oss-120b`.** Originally specced against
  Anthropic/OpenAI; switched to Groq because that was the available key.
  `llama-3.3-70b-versatile` (the originally planned model) has been retired on
  Groq and no Llama 70B remains on the account, so `openai/gpt-oss-120b` — the
  closest current large instruct model with JSON-mode support — was used. The
  call has an 8s timeout and a deterministic keyword-parsing fallback, so the
  product still works with no API key at all. See `api/app/intent.py`.
- **Models and data are committed** (`api/models/*.joblib`, `api/data/*.parquet`)
  so the deployed service and these numbers reference byte-identical artifacts —
  build-time training could drift across platforms at the floating-point level.
- Prices are in **lakh (₹100,000)** everywhere; conversion to rupees happens only
  in the UI display helpers.

## Run locally

Backend (FastAPI, needs [uv](https://docs.astral.sh/uv/)):

```bash
cd api
uv sync
# data/ and models/ are committed; regenerate only if you want to:
#   uv run python -m app.generate_data   # writes data/*.parquet
#   uv run python -m app.train           # writes models/*.joblib + metrics.json
uv run uvicorn app.main:app --reload --port 8000
uv run python evals/run_evals.py         # prints field accuracy + price leakage 0
uv run pytest -q
```

Create `api/.env` from `api/.env.example` and set `GROQ_API_KEY` (optional — the
keyword fallback runs without it).

Frontend (Vite + React + TS):

```bash
cd ui
npm install
echo "VITE_API_URL=http://localhost:8000" > .env.local
npm run dev
```

## Deploy

- **API → Render** (`render.yaml`): committed artifacts mean the build is just
  `uv sync --frozen --no-dev`; start binds to `$PORT`. Set `GROQ_API_KEY` in the
  dashboard. Free tier sleeps after ~15 min idle, so a keep-alive pings `/health`.
- **UI → Vercel**: root `ui/`, `VITE_API_URL` set to the Render URL. Nothing
  `VITE_`-prefixed may hold a secret — it is compiled into the public bundle, so
  the Groq key lives only on the API.

## What I'd do next

- **Per-dealer sell-through personalisation** — learn each dealer's actual
  turn-time and realised margins and re-weight ranking per dealer, instead of one
  global days-to-sell model.
- **Photo-based grade inference** — infer the A/B/C inspection grade from
  listing photos rather than taking it as a given field.
- **Live auction integration** — real inventory, real reserve prices, and a real
  (still dealer-confirmed) bid path, replacing the synthetic generator.
